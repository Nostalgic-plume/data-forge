# DataForge — 智能数据生成平台（完整计划书）

> 状态：已定稿（2026-08-10）｜用途：秋招面试项目 + 自用数据生成工具

## 1. 项目定位

**一个"理解你的项目"的数据生成平台**：给定数据库连接 + 项目源码路径，自动分析项目业务规则 → 生成关联完整、语义真实的数据 → 校验修正 → 落库。核心卖点：**三 agent 协作 + 连库校验修正 + 手写 ReAct 循环**。

差异化：现有开源工具（SDV/Gretel）是"约束驱动"（用户手写约束定义），DataForge 是"**agent 自动理解项目**"（分析 agent 提炼规则，人工兜底确认）。

## 2. 技术栈

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Java 21 LTS | 虚拟线程叙事 |
| LLM 接入 | Spring AI 1.x（ChatClient + Tool Calling） | Spring 生态正统 |
| Agent 循环 | 手写 ReAct（不引 agent 框架） | 全叙事权 |
| 数据库 | MySQL 8（staging 工作库） | 连库卖点 + 回滚 |
| 前端 | Vue3 + TS + Vite + Element Plus + ECharts + SSE | 复用既有技能，开发最快 —— **P7 实际落地：静态 index.html 原生 JS + fetch**（完整 Vue3 向导 + ECharts 为后续增强） |
| 模型 | 主：deepseek-v4-flash；备：qwen-flash（DashScope 兼容端点）；分析用 pro 级 | 主备双链路 + 按角色分模型 |
| 凭证 | 环境变量注入 | 安全规范 |

## 3. 总体架构

```
用户输入：数据库连接 + 项目路径 + skill 选择（自动检测+手动）
    │
    ▼
① 分析 agent（知识层，可缓存）
    子任务并行：表结构 / 枚举状态 / 关联关系 / 列语义提炼（规格体系）/ 业务规则
    skill 机制：通用清单（列语义提炼）+ 垂直清单（电商规格，按领域加载）
    工具层（P6）：MCP 客户端（mysql-mcp 读库结构 + 源码读取/搜索工具）——LLM 自主调用
    产出：project_rules.md 母版（前置约束节 + 后置修正规则节）+ 行数推荐 + 行构建器定义(YAML)
    人工检查点：约束清单确认/修改（用户声明 > agent 推断）
    置信度标注：每条规则带置信度，低置信度项优先人工确认
    │
    ▼
② 生成 agent（内容层）
    LLM 样本（仅 3 张语义源表：category/user/product）+ 锚点派生
    展开器（P1）：规格蓝图 × 锚点 → 全量（秒级，零 LLM）
    管线：PK 骨架（起始 ID 可配）→ FK 分配 → DAG 并发生成 → 后处理
    并发：表间 DAG 并行 + 表内批次并行（虚拟线程）
    缓存：样本 + 展开参数（DDL 指纹 + 种子命中），生成层可整体跳过
    增量模式：只生成新增部分（现有池引用 + 起始 ID=MAX(id)+1），全量是增量的特例
    容错：失败表隔离（单表失败不 abort 全局，标记继续最后汇总）+ batch 自适应（截断自动降批）
    真实感：FK 权重分布（幂律长尾：少数用户多订单，多数用户少订单）+ 确定性种子（可复现）
    质量：样本预检（展开前先校验样本，早期止损）+ 数据血缘标注（每字段来源：规则/FK/LLM/修正）
    续跑：断点续跑（中途失败从断点继续，不从头重来）
    │
    ▼
③ 修正 agent（质量层，流水线式）
    修正调度器：任务依赖图（表对粒度），表完成事件即触发
    收敛循环（ReAct）：校验报告 → 报告压缩（分桶）→ LLM 桶决策（并行）
      → 应用修正（id 锚定 + 列级最小干预）→ 再校验
    收敛控制：问题清单闭环（新错误=回归=回滚）+ 通过率上升 + max_iterations 放宽
    双通道：规则通道（FK/去重/格式）优先，LLM 通道只处理语义修正
    并行安全：桶决策并行时，命中同一行的桶自动串行化（防互相覆盖）
    作用域限定：增量时只修正新 ID 区间，绝不触碰现有数据
    │
    ▼
④ 校验器（规则引擎，非 LLM）
    通用规则：从 DDL 元数据自动推导（FK/唯一/非空/格式）→ 生成检查 SQL
    项目规则：从 project_rules 后置节编译（金额对账/状态联动/快照一致）
    Detect（全量 SQL 扫描）→ Aggregate（根因分桶 + 样本 + 根因假设）
    跨现有校验：增量时父表引用需同时读现有数据 + 新增数据
    │
    ▼
⑤ 软评分（P7）：统计距离度量（借鉴 SDMetrics：KS/JS 分布距离）+ 语义抽样 LLM 打分
    │
    ▼
staging 落库（隔离工作库）→ 人工确认报告 → 按保留策略发布到目标库
（保留策略：REPLACE 清空重建 / APPEND 追加 / KEEP 不动，按表独立配置；危险操作二次确认 + 自动备份）
```

## 4. 核心设计决策（29 项）

1. **约束母版分派**：project_rules.md 一份（人工编辑），编译时拆分 generation_prompt / correction_rules，角色隔离上下文
2. **LLM 发现、代码执行**：规则提炼用 LLM（一次性+人工确认），规则执行用确定性代码（校验 SQL/修正应用），信任模型红线
3. **最小干预修正**：列级修复 + id 锚定（整行语境决策、精确落位）+ 规则级批量（同根因一个模板）+ 严重乱行整行重写兜底
4. **报告压缩**：Detect→Aggregate 分桶，LLM 只看 {数量,占比,样本,根因假设}，不看全量
5. **收敛防回归**：问题清单闭环（修报告内的问题，新错误=回归=回滚）
6. **staging 落库**：生成/修正/校验在隔离工作库，收敛+人工确认后发布，回滚=重建工作区
7. **两阶段生成**（P1）：LLM 只产样本（语义），规则展开规模（锚点+蓝图派生），"LLM 定义模板、规则实例化"
8. **生成缓存**：样本+参数落盘，改修正规则只重跑修正（迭代周期 2h→5min）
9. **补差不重试**：验证差 ≤2% 直接接受，超出补缺行，不整批重试
10. **错误注入**（P7）：规则引擎反向执行，按注入率配置制造真实世界的脏数据（容错测试 + 真实感瑕疵）——**P8 按用户要求移除，不实现**（2026-08-22）
11. **skill 机制**：子 agent 是容器（通用），skill 是内容（按领域加载），用户显式选择 > 自动检测
12. **模型容错**：LlmProvider 抽象，主备双链路，5xx/限流自动 failover
13. **保留策略**：REPLACE / APPEND / KEEP 按表独立配置，staging 先行 + 危险操作二次确认 + 自动备份，目标库变更永远是显式的最后一步
14. **增量生成**：全量是增量的特例——增量 = 现有池引用 + 起始 ID=MAX+1 + 修正作用域限定新区间 + 校验跨现有数据；**缓存 key 含 baseline**，目标库变化即失效
15. **读 MCP、写 JDBC**：分析 agent 读库结构走 MCP 标准协议（LLM 自主）；校验/修正/发布走独立确定性 JDBC 通道（性能、事务、可并发），MySQL 方言层预留接口
16. **断点续跑**：生成/修正中途失败从断点继续（幂等 + 缓存），不从头重来
17. **数据血缘**：每字段标注来源（规则/FK/LLM/修正），导出带出——调试与面试加分
18. **成本记录**：历史记录含 token 消耗/耗时/成本，模型对比的量化依据
19. **三层分工**：分析 agent 决策（产文档含参数，RuleSetters 定参）→ 生成 agent 执行（读文档传参，不自主发明）→ 修正 agent 质量（统一引擎贯穿三阶段）
20. **传参边界**：有语义价值的规则参数传参（PK 类型/初始值、枚举值/权重、锚点/蓝图）；格式类（地址/电话/邮箱/日期/图片）直接调用规则工具不传参
21. **文档单一事实**：project_rules 是唯一参数源；修正 agent 阶段 A 校验后基本无缺口，真缺口上报人工
22. **质量守护贯穿**：修正 agent = 统一"校验→修正→再校验"引擎，应用三阶段（分析产物/固定值/最终数据），规则优先 LLM 兜底，兜不住人工
23. **收敛目标 B**：硬错误 ≥98% 收敛，残余问题写入最终报告（可追踪不静默）
24. **对话式询问（HITL）**：ask_user 通道 + 触发门控（值得问才问）+ 询问频率设置（始终/关键/不问）
25. **修正 SQL 化**：修正执行 = 受控 SQL 方法（批量秒级），规则匹配优先（90%+ 桶零 LLM），LLM 只处理需语义理解的修正值；check→apply→check 循环
26. **列生成指令**：列分类规则（分析 skill）→ 列生成指令（文档，每列 mode/tool/anchor）→ 工具注册（生成 agent），LLM 不猜映射只拿可调方法清单
27. **血缘可见性**：数据血缘展示来源类型（规则/LLM/锚点/枚举/FK），列生成指令（具体方法调用）隐藏不展示
28. **流式输出**：分析 agent 结果 SSE 流式展示（子任务/规则渐进呈现）
29. **生成 agent 最小 LLM 使用**：LLM 只生成语义列值（E）+ 硬缺口 ask_user 上报，不调读库/读项目工具（业务信息来自分析文档）；扩展点：可选只读查询工具（第一版不做）

## 5. 模块清单（接口层，防死代码）

```
com.dataforge
├── agent/                    # 三 agent 入口（唯一对外入口）
│   ├── AnalysisAgent         # 分析：项目 → project_rules + 行数推荐 + 行构建器
│   ├── GenerationAgent       # 生成：样本 + 展开参数 → 全量（支持增量模式：现有池引用）
│   └── CorrectionAgent       # 修正：数据 + 校验报告 → 修正后数据
├── validation/
│   ├── Validator             # 校验器（Detect + Aggregate）
│   ├── RuleCompiler          # project_rules 后置节 → 检查 SQL
│   └── Scorer                # 软评分（统计距离 + 语义抽样）
├── expansion/                # 展开器（P1）
│   ├── ExpansionEngine       # 样本 → 全量（执行 YAML 行构建器）
│   └── BuilderRegistry       # 行构建器注册（YAML 解析）
├── pipeline/                 # 移植自 real-world-data（功能提取）
│   ├── PkGen / FkAlloc / ContentGen / PostProcess
│   └── TopologicalSorter      # 拓扑图（生成/修正共用）
├── db/
│   ├── McpClient             # MCP 客户端：分析 agent 读库结构/源码（P6）
│   ├── JdbcDataSource        # 确定性 JDBC 通道：校验/修正/发布/baseline（MySQL，方言层预留）
│   ├── StagingManager        # staging 工作库生命周期
│   └── Publisher             # 按保留策略(REPLACE/APPEND/KEEP)发布 + 安全预检确认
├── llm/
│   ├── LlmProvider           # 模型抽象（主备 failover）
│   └── ReActLoop             # 手写 ReAct 循环（工具注册/历史/终止）
├── skill/
│   ├── SkillRegistry         # skill 加载（通用 + 垂直）
│   └── skills/ecommerce.md   # 电商垂直清单（规格体系等）
├── cache/                    # 分析产物/生成样本缓存（git HEAD + DDL 指纹）
├── inject/                   # 错误注入器（P7）
└── web/                      # Spring Boot REST + SSE + Vue3 前端（历史记录含 token/耗时/成本）
```

**接口治理纪律**（死代码防护）：
- 对外只有上面列出的入口；管线内部类一律 `package-private` 或内部实现
- 不做 YAGNI：计划书中标"P1/P6/P7"的组件不在一版实现，但**接口位置预留**（如 BuilderRegistry 先有空实现）
- 每条规则/每个工具函数必须有消费方；删除时先 grep 调用链

## 6. 数据模型

```markdown
project_rules.md（母版，人工编辑）
├─ # 前置约束（编译 → generation_prompt，注入生成 agent）
│   - orders.status 权重分布，绝大多数 4
│   - 商品名风格：品牌+型号
├─ # 后置修正规则（编译 → correction_rules + 校验 SQL）
│   - 金额对账: total = Σ(subtotal)；actual = total - discount + freight
│   - 状态联动: status=4 必须有 pay→deliver→receive 且递增
└─ # 行构建器（YAML，P1 展开器执行）
    sku:
      specs: {模板: "规格蓝图", 系数表: {标准版:1.0, 高配版:1.2}}
```

```json
// 校验报告（压缩后，喂 LLM 的格式）
{"buckets": [
  {"table":"orders","col":"actual_amount","type":"MISMATCH",
   "count":1832,"ratio":0.61,"samples":[{...3条整行快照}],"rootCause":"discount 未重算"}]}
```

```json
// 修正输出（id 锚定）
{"id":342, "fixes":{"original_price":1599.00}}
```

```json
// 保留策略（按表独立配置，发布层执行）
{"orders": "REPLACE", "product": "REPLACE", "role": "KEEP", "user": "APPEND"}

// 增量配置（生成层，全量是增量的特例：mode=full）
{"mode": "incremental", "baseline": {"orders": 5509}, "scope": ["orders", "order_item"], "newUsers": 10}
```
## 7. 性能设计（实测基准：12526 行 2.5h → 目标 20min 内）

| 优化 | 杠杆 | 阶段 |
|---|---|---|
| 两阶段生成（样本+展开） | 最大：LLM 调用次数 ÷5~10 | P1 |
| 数值列锚点派生 | 每行 LLM 列数减半 | P1 |
| 补差不重试 | 消除 2-3 倍重试放大 | P0 |
| 表内批次并行（6-8 路，防限流） | 并行度 ×6~8 | P0 |
| 生成缓存 | 调规则迭代 2h→5min | P0 |
| batchSize 100→200（64K 输出） | 调用次数减半 | P0 |

## 8. 开发阶段（P0-P8，含验收标准）

| 阶段 | 内容 | 验收 | 面试叙事 |
|---|---|---|---|
| P0 | Spring AI 接入 + 管线移植（表间并发/补差/缓存/断点续跑/batch） | 纯 CLI 能生成 shop 全量数据 | LLM 接入、管线、并发 |
| P1 | 展开器 + 锚点派生 + FK 权重分布 + 样本预检 | 生成时间达标（20min 内）+ 订单在用户间呈长尾分布 | 性能工程、真实感 |
| P2 | 连库层 + 校验器（通用+金额规则） | 校验报告正确分类问题 | 工具调用、规则引擎 |
| P3 | 修正 agent 单任务循环（id 锚定/收敛/回滚/桶冲突串行） | 金额错误自动收敛为 0，同批修正不互相覆盖 | ReAct、收敛控制 |
| P4 | 流水线修正（表完成事件） | 小表修正不阻塞大表生成 | 事件驱动、任务依赖图 |
| P5 | 增量生成（现有池引用 + 起始 ID + 作用域限定 + 跨现有校验） | 现有数据保留，追加不冲突不误伤 | 增量架构、数据安全
| P6 | 分析 agent + project_rules + skill + 缓存（含置信度标注） | 自动提炼 shop 规则，低置信度项可确认 | 知识提炼、上下文工程 |
| P7 | 软评分 + Web 界面（五步向导 + 历史页） | 全流程浏览器可跑 | 评估体系、全栈 |
| P8 | 错误注入 + 多模型 failover | 注入配置生效 | 容错测试、可靠性 |

> 测试纪律：每个阶段验收均含 mock LLM 单元测试 + 校验器规则测试 + 集成测试（借鉴 real-world-data 的 mock 先例）——后续优化的正确性前提
> 面试底线：P0-P3 闭环（CLI 可演示）+ P6 分析 agent = 完整故事；P4 流水线修正与 P5 增量为加分。P7/P8 按时间弹性取舍。

## 10. 风险与边界（诚实声明）

- 分析 agent 提炼"可发现的规则"，深层业务规则靠人工补（约束确认页就是兜底）
- 收敛无理论保证：max_iterations + 回滚 + 上报人工
- 模板派生有机械感：样本设计决定上限（换时间，值）
- 单模型依赖：主备 failover 缓解，不根治
- agent 系统自身需要测试：模拟 LLM 的单元测试必须保留（借鉴 real-world-data 的 mock 测试）
- 误删风险：staging 先行 + 危险操作二次确认 + 自动备份三层防护，但 REPLACE 仍依赖用户确认

## 11. 面试叙事点汇总（一个故事讲完）

> "我构建了一个能理解项目的合成数据生成平台。核心是三个 agent：分析 agent 用子任务并行提炼项目业务规则（配 skill 机制，用户可确认兜底）；生成 agent 用 LLM 产样本、规则引擎扩规模（成本从 2.5 小时压到 20 分钟）；修正 agent 手写 ReAct 循环，用 id 锚定做最小干预修复，用问题清单闭环防回归，整个流程跑在 staging 隔离库上，收敛后才发布。校验器是确定性规则引擎，规则从 DDL 元数据自动推导——LLM 只负责发现规则，代码负责执行规则，这是可靠性的底线。我的架构和 ICLR 2026 的 AgentSynth（Proposer/Verifier/Reviser 接力）同构，但它是学术框架，我落地到了真实电商场景，产出的数据真实解决了当前数据库 4860 条悬挂订单的问题。目标库已有数据时按保留策略（REPLACE/APPEND/KEEP 按表独立）处理，增量模式复用现有数据池、修正作用域限定新区间、校验跨现有数据，全量只是增量的特例。"
